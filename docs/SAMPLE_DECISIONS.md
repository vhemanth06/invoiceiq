# Sample decisions

What each sample in `samples/invoices/` should return. Every decision below was checked with a live Groq run
of the samples in order on fresh data.

- **01–09** are generated by `samples/generate_samples.py`. They are listed in `samples/manifest.yaml`, and the
  golden tests (`tests/test_edge_cases.py`) check them.
- **10–11** were added by hand. They are in the manifest (so the demo and CLI run them) but not in the
  golden tests, which have no ground-truth file for them.
- **12** is generated and is in the manifest and the golden tests.

## Run them in this order, on fresh data

Samples 04 and 05 depend on invoices recorded earlier (the running PO ledger and the duplicate check).

1. Setup page → **Reset demo data** (or `python -m core.db.seed`). The Process Invoice page's
   **Demo: run the sample invoices** section does this reset and runs every sample in order for you.
2. Upload 01 → 12 one by one on the Process Invoice page, in number order.
   Or from a terminal: `python cli.py --all-samples --reset` runs all 12 and prints PASS / MISMATCH per
   sample.

Running a sample twice gives a different answer the second time: the repeat is caught as a duplicate of the
first run (same file) and is **REJECTED**. Reset demo data before re-running the set.

## Each sample

### 01 · Happy path → APPROVE
- **Invoice:** 40 gloves × ₹1,500 + 20 hoses × ₹2,000 = ₹1,00,000, plus CGST 9% and SGST 9% = ₹1,18,000.
- **Why:** everything checks out.
  - The vendor is approved, and the GSTIN and bank account (…4521) match the vendor master.
  - PO-2026-1041 is referenced and exactly covers the amount.
  - The arithmetic and the GST split are correct.
- **Findings you will see:** all checks pass. One Info: the date `05/10/2026` is read as 5 Oct 2026
  (Indian DD/MM).
- **Action shown:** schedule payment of ₹1,18,000.

### 02 · Split invoice, milestone 1 → APPROVE
- **Invoice:** ₹2,00,000 + IGST 18% = ₹2,36,000. The PO is written as `PO 1052` and the date as `1-Sep-26`.
- **Why:** PO-2026-1052 (₹5,90,000) allows partial billing, and ₹2,36,000 is well inside it.
- **Findings:** all pass.

### 03 · Split invoice, milestone 2 → APPROVE
- **Invoice:** ₹1,80,000 + IGST = ₹2,12,400. The date is written as `2026-10-01`.
- **Why:** the running total, ₹4,48,400, is still under the PO's ₹5,90,000.
- **Findings:** all pass.

### 04 · Split invoice, milestone 3 → REVIEW
- **Invoice:** ₹1,62,000 + IGST = ₹1,91,160. The PO is written as `#1052`.
- **Why:** on its own the invoice looks fine. But the three invoices total ₹6,39,560 against a ₹5,90,000 PO,
  which is **8.4% over**. That is above the ₹5,000 tolerance but below the 10% hard-block line, so the result
  is REVIEW, not REJECT.
- **Findings (Warn):**
  - `R16_CUMULATIVE_PO`: cumulative billing exceeds the PO value by ₹49,560 (+8.4%).
  - `R15_AMOUNT_TOLERANCE`: the invoice exceeds the PO's remaining ₹1,41,600.
  - `R18_LINE_PRICES`: milestone 3 is billed at ₹1,62,000 vs ₹1,20,000 on the PO line (+35%).
- **Action shown:** hold payment; request a credit note for ₹49,560 or a PO amendment.
- **Needs:** 02 and 03 run first.

### 05 · Disguised duplicate (scanned) → REJECT
- **Invoice:** same goods and amount as 01, renumbered `INV/1042-R`, dated 26/10/2026, and marked
  "Reminder copy". It is an image-only scan, so the file differs from 01.
- **Why:** the invoice number normalises to `1042`, the same key as 01 for the same vendor, so it is an exact
  duplicate.
- **Findings:**
  - `R19_EXACT_DUPLICATE` (Block): duplicate of INV-1042, with a link to 01's run.
  - `R16_CUMULATIVE_PO` (Block): PO-2026-1041 would be billed 100% over.
  - `R15_AMOUNT_TOLERANCE` (Warn): nothing is left on the PO.
- **Action shown:** do not pay; return to the vendor as a duplicate.
- **Needs:** 01 run first. Without 01 in history it would come out APPROVE.

### 06 · Tax-inclusive pricing → APPROVE
- **Invoice:** 2,000 boxes × ₹33.60 + 120 rolls × ₹224 = ₹94,080. The prices *include* 12% GST
  (a footnote shows CGST ₹5,040 + SGST ₹5,040).
- **Why:** a naive check compares ₹94,080 with the PO subtotal of ₹84,000 and sees a 12% "overcharge".
  InvoiceIQ removes the included tax first: ₹94,080 / 1.12 = ₹84,000, which matches the PO. Unit prices are
  compared without tax too (₹30 and ₹200, matching the PO).
- **Findings:** all pass. One Info: `R21_TAX_RECONCILED`, the 12% difference is fully explained by GST
  included in the prices.

### 07 · Scanned, no PO, stained total → REVIEW
- **Invoice:** "Hosting services – Oct 2026", ₹60,000 + IGST = ₹70,800. It is a rotated, noisy scan with a
  stain over the total, and no PO number is printed.
- **Why:** the PO is only inferred, and inferred PO matches are never auto-approved.
- **Findings (Warn):**
  - `R12_PO_INFERRED`: likely PO-2026-1071, scoring well above the runner-up PO-2026-1075. This always fires.
  - `R02_CONFIDENCE`: the total was read with confidence below 0.80. This fires only if the model is unsure
    of the stained total. The offline test data sets 0.55, but in the live Groq run the total was read
    confidently and this check passed.
- **Action shown:** confirm the PO with the requester, and verify the total if `R02` fired.

### 08 · Bank account changed → REVIEW
- **Invoice:** 50 bearing kits × ₹1,000 = ₹50,000 + GST = ₹59,000, matching PO-2026-1044 exactly, with a
  note "Please note our NEW bank account details".
- **Why:** the account ends in 9931, but the vendor master says 4521. A changed bank account is a classic
  payment-diversion fraud pattern, so it always goes to a human.
- **Findings (Warn):** `R11_BANK_MATCH`: invoice account …9931 vs master …4521.
- **Action shown:** verify the change by calling the vendor on the number in the vendor master.

### 09 · Unapproved vendor → REJECT
- **Invoice:** Orbit Office Solutions, 10 chairs × ₹8,500 = ₹85,000 + IGST = ₹1,00,300, quoting
  PO-2026-1099.
- **Why:** Orbit is in the vendor master but not approved (KYC pending).
- **Findings:**
  - `R09_VENDOR_APPROVED` (Block): the vendor is not approved.
  - `R12_PO_MISSING` (Warn): PO-2026-1099 does not exist.
- **Action shown:** return to the vendor; complete onboarding/KYC first.

### 10 · Foreign currency (USD) → REVIEW
- **Invoice:** Acme INV-1077, 50 bearing kits × USD 12 = USD 600, plus CGST 9% and SGST 9% = **USD 708**,
  quoting PO-2026-1044 (an INR PO for ₹59,000). The footer says "All amounts are in US Dollars (USD)".
- **Why:** POs, tolerances and the ledger are all in INR. Comparing USD 708 with ₹59,000 number for number
  would be meaningless, so a non-INR invoice always goes to a human.
- **Findings (Warn):** `R24_CURRENCY`: invoice currency USD.
- **Action shown:** convert at the contracted rate and confirm the PO currency before paying.
- **Note:** when it runs after 08, which already billed ₹59,000 on PO-2026-1044, the small USD 708 still
  falls inside the PO tolerance (₹1,180), so currency is the only flag. Run on its own, it would also flag
  `R17_PARTIAL`, because ₹708 is far below the PO. It is REVIEW either way.

### 11 · Clean scan with PO → APPROVE
- **Invoice:** Nimbus NCH-2026-1121, an image-only scan with no text layer. "Backup storage add-on 2 TB",
  1 × ₹15,000 + IGST 18% = ₹17,700, quoting PO-2026-1075 (₹17,700). The date is `05/11/2026` and the bank
  account ends in 6650.
- **Why:** it is routed to the vision model and reads cleanly. The PO is explicit and exactly covered, and
  the vendor, GSTIN, bank and inter-state IGST all match. Unlike 07, which has no PO number, a scanned
  invoice like this one can be auto-approved when it is readable and fully matches.
- **Findings:** all pass. One Info: the date `05/11/2026` is read as 5 Nov 2026 (Indian DD/MM).
- **Action shown:** schedule payment of ₹17,700.
- **Needs:** `GROQ_VISION_MODEL` set, because it is a scan. Without it the result is "Manual entry
  needed" → REVIEW.

### 12 · Unknown PO → REVIEW
- **Invoice:** Deccan Packaging DPC-5600, dated 11/11/2026, "Your Ref: PO-2027-1900". One line, "something",
  1 × ₹1,20,000 + CGST 6% ₹7,200 + SGST 6% ₹7,200 = ₹1,34,400. Bank …3302.
- **Why:** PO-2027-1900 is not in the purchase-order list. Because the reference states a year, it is not
  silently remapped to another PO. InvoiceIQ then tries to infer a PO from Deccan's open POs. The only
  candidate, PO-2026-1063, is already fully billed by sample 06 and its lines don't match, so no PO is
  accepted. Without an approved PO there is no proof the purchase was authorised, so it goes to a human.
- **Findings (Warn):** `R12_PO_MISSING`: reference 'PO-2027-1900' does not exist (candidate listed:
  PO-2026-1063). Vendor, GSTIN, bank, arithmetic and GST all pass; the PO-amount rules are skipped because
  there is no PO.
- **Action shown:** confirm the purchase order with the requester before paying.
- **Note:** if someone adds PO-2027-1900 on the Setup page, this invoice matches it and comes out APPROVE.
  Reset demo data reseeds POs from the CSVs, which do not contain it.

## If you get a different answer

- **Everything REJECT:** the samples were already run once; reset demo data.
- **05 APPROVE:** 01 was not run first, or was rejected or overridden to REJECT.
- **04 APPROVE:** 02 and 03 were not run first.
- **12 APPROVE:** PO-2027-1900 was added on the Setup page; reset demo data to remove it.
- **REVIEW with "Manual entry needed":** the LLM could not read the file. Check the Extract stage message.
  Common causes: no Groq key, the daily quota is used up, or no vision model is set for the scanned
  samples 05, 07 and 11.
- **Rule thresholds changed in Setup:** results follow the new thresholds, not this table.
